Мы продолжаем учебный исследовательский проект «Поездка: бюджет и маршрут» по сравнению workflow, одиночного LLM-агента и мультиагентной системы (MAS).

Первый день разработки предположительно завершён: должны быть реализованы схемы JSON, загрузчик, проверка ссылок, базовый валидатор и CLI. Однако не считай это гарантированным — сначала проведи аудит репозитория.

**Твоя задача: составить подробный, технически конкретный план всей оставшейся реализации до промежуточного показа. Пока ничего не реализуй.**

## 1. Аудит текущего состояния

Изучи весь репозиторий, README, AGENTS.md, зависимости, исходные данные, сценарии, тесты и существующие команды запуска.

Определи:
- Что уже реализовано и действительно работает.
- Какие проверки есть в валидаторе.
- Насколько заполнены JSON-каталоги реальными данными.
- Есть ли полностью заполненный и корректный `dev_01`.
- Какие части отсутствуют или реализованы частично.
- Какие решения можно использовать повторно без переписывания.

Запусти доступные тесты и CLI. Не изменяй исходные данные других участников.

## 2. Цель промежуточного показа

Нужно реализовать и сравнить три подхода:

**A. Fixed workflow**

Заранее определённая последовательность: анализ запроса → поиск кандидатов → уточнение предпочтений → построение вариантов → проверка → исправление → итог.

**B. Single-agent**

Один LLM-агент самостоятельно выбирает инструменты, последовательность действий, уточняющие вопросы и способы исправления ошибок.

**C. MAS с координатором**

Координатор и специализированные агенты:
- транспорт;
- проживание;
- места и отзывы;
- маршрут и логистика;
- верификация.

Специалисты самостоятельно принимают решения в своей области. Координатор согласует результаты и организует адресные исправления.

Вторую MAS без координатора и полноценные абляции сейчас НЕ реализуем.

## 3. Общая инфраструктура

Запланируй реализацию:

- Полного валидатора бюджета, времени, перемещений, часов работы, заселения, обязательных ограничений и источников.
- Общих инструментов поиска по локальным JSON.
- Общего клиента LLM с конфигурацией модели, параметрами генерации, таймаутами и ограничениями.
- Единого формата входа и выхода для трёх подходов.
- Логирования действий, токенов, стоимости, времени и ошибок.
- Механизма до трёх уточняющих вопросов за запуск.
- Симулятора пользователя со скрытыми предпочтениями.
- Формирования до пяти содержательно различных вариантов поездки.
- Проверки жёстких ограничений, Парето-фильтрации и выбора подходящих компромиссов.
- Независимого оценщика, который не раскрывает скрытый профиль агентам.

На первом этапе все подходы используют один сохранённый каталог данных. API внешних источников транспорта, жилья и карт пока не подключаем.

API языковой модели, напротив, подключаем для реализации LLM-архитектур.

## 4. Сценарии и эксперименты

Сначала доводим до рабочего состояния один сценарий `dev_01`.

Затем готовим:
- 4 сценария для разработки;
- 12 тестовых сценариев;
- проверенные разрешимые случаи;
- несколько сценариев с конфликтами;
- случаи с разными скрытыми предпочтениями;
- сценарии изменения условий поездки.

Проводим сравнение трёх архитектур на одинаковых данных.

Основные метрики:
- Success@1;
- Success@5;
- доля корректных планов;
- соответствие скрытым предпочтениям;
- число уточняющих вопросов;
- количество вызовов LLM;
- входные и выходные токены;
- количество вызовов инструментов;
- полное время выполнения;
- стоимость одного запуска.

Желательно выполнить два повтора на каждом из 12 тестовых сценариев, если позволяют ресурсы.

Нужны автоматические отчёты в CSV/JSON, сравнительная таблица, графики и несколько разобранных успешных и неуспешных трасс.

## 5. Требования к архитектуре

Необходимо обеспечить честное сравнение.

У всех подходов должны быть одинаковые:
- исходные данные;
- инструменты;
- модель и параметры генерации;
- доступ к уточняющим вопросам;
- ограничения по ресурсам;
- формат результата;
- независимые правила оценки.

Различаться должна именно организация решения задачи.

Не допускай утечки скрытых предпочтений в контекст планировщиков. Не делай общий инструмент, который фактически полностью решает задачу за все архитектуры.

Нельзя подменять реальные LLM-эксперименты имитацией успешных ответов.

Предусмотри возможность запуска без API-ключа для структурных тестов, но реальные эксперименты должны явно требовать корректно настроенный LLM API.

## 6. Как составить план

Разбей оставшуюся работу на последовательные этапы:

1. Аудит и устранение недочётов первого дня.
2. Завершение общей инфраструктуры и валидатора.
3. Реализация fixed workflow.
4. Реализация single-agent.
5. Реализация MAS с координатором.
6. Подготовка набора сценариев и независимого оценщика.
7. Проведение экспериментов.
8. Анализ результатов и подготовка материалов к показу.

Для каждого этапа укажи:
- конкретные задачи;
- какие файлы создать или изменить;
- архитектурные решения;
- зависимости от предыдущих этапов;
- тесты;
- критерии готовности;
- ожидаемые результаты.

Отдельно опиши структуру проекта, интерфейсы модулей, конфигурацию LLM, формат логов и запуск экспериментов.

## 7. Важные ограничения

- Не переписывай работающие компоненты без необходимости.
- Не меняй собранные командой реальные данные ради прохождения тестов.
- Не выдумывай цены, расписания, источники или результаты экспериментов.
- Если данных недостаточно, укажи конкретные пробелы и предложи способы их устранения.
- Не усложняй архитектуру без исследовательской необходимости.
- Предусмотри возможность реализовывать и тестировать этапы независимо.
- Не переходи к живым внешним API до завершения первого сравнения.
- Все решения должны быть воспроизводимыми.
