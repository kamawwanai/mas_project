# Протокол сравнительных экспериментов

Среда фиксирована: 17–18 октября 2026 года, `benchmark_assumptions`.
Она не подтверждает исторические предложения. Режим `strict` остаётся отдельным.

Все архитектуры получают одинаковые публичные условия, каталоги, атомарные
инструменты и лимиты ресурсов. Будущие запуски используют одну точную модель
и одинаковые параметры генерации. У MAS учитываются координатор и специалисты.
Workflow имеет фиксированные этапы и до двух исправлений; single-agent выбирает
действия сам; MAS делегирует пяти специалистам с отдельными историями.
Финальный кандидат MAS требует успешного вызова validate_plan специалистом
verification, связанного с точными хешами плана, запроса и каталогов.

Четыре dev-сценария служат отладке, двенадцать test фиксируются до сравнения.
Порядок запусков перемешивается воспроизводимым seed. Повторы и бюджеты общие.
Oracle-scripted mock не включается в результаты качества моделей.

## Приватность

Профили и веса находятся в `evaluation/benchmark/profiles/`; частный дизайн —
в `evaluation/benchmark/design_profiles.json`. Планировщикам эти файлы, эталоны,
альтернативы и сертификаты не передаются. Вопрос раскрывает только одну тему:
интересы, темп, комфорт, экономию, тишину или расположение. Лимит — три вопроса
на весь запуск со всеми специалистами и версиями перепланирования.

## Оценка

Success@1: первый маршрут проходит все жёсткие ограничения и имеет приватную
полезность >= 0.7. Success@5: такой маршрут есть среди максимум пяти различных
результатов одного запуска. Дубли и малые изменения времени/текста не помогают;
разные заведения питания учитываются. Отдельно сохраняются Feasible@K,
полезность, доля допустимых планов, вопросы, инструменты, попытки LLM, токены,
время и стоимость. Парето-отбор учитывает цену, ходьбу, время пути и признаки.

Культура и питание агрегируются по соответствующим объектам, комфорт, тишина
и расположение — по заданным признакам жилья. Темп отражает ходьбу, экономия —
остаток бюджета. Это условные прокси, не эмпирические человеческие оценки.
Приватные веса влияют на полезность, не на допустимость.

Сертификаты невозможности пересчитываются по замкнутому синтетическому каталогу:
нижняя граница обязательных расходов превышает бюджет либо обязательное место
закрыто на все даты. Они не доказывают невозможность реальной поездки.

## Изменения и отчёты

dev_04 и test_11 снижают бюджет, test_12 делает выбранное жильё недоступным.
Начальная и финальная версии оцениваются отдельно; ресурсы накопительные.
Оплаченных обязательств и штрафов отмены в этой среде нет.

Манифест связывает код, запрос, профиль, каталог, кейс и реестр хешами. Трассы,
результаты, кандидаты, оценка и сводка запечатываются контролем целостности.
Resume пропускает только целые неизменённые результаты; частичный запуск
сохраняется для отдельного разбора. Отчёты запрещают смешивание режимов клиента
и разных сред. Mock CSV/JSON и графики явно помечены MOCK / SYNTHETIC.
Готовность benchmark не является разрешением подключить API.

## Условия честного сравнения перед LLM-пилотом

Общая библиотека содержит десять инструментов. Workflow открывает их по стадиям:
поиск читает каталог, уточнение вызывает ask_user, проверка вызывает validate_plan,
исправление может использовать весь набор. Single-agent выбирает действия самостоятельно.
Координатор и специалисты MAS используют тот же набор; дополнительный delegate управляет
делегированием и тоже расходует лимит инструментов. Вызовы специалистов последовательны.
Отдельных бюджетов специалистов нет: один Runtime учитывает всю архитектуру и все версии.
Фиксированные проверки workflow также учитываются как вызовы инструментов.

У всех архитектур есть одинаковый завершающий select: жёсткая проверка, Парето-фильтрация,
удаление дублей и ранжирование по публичным условиям и раскрытым ответам. Поэтому Success@1
оценивает итог после общего отбора, а не исходный порядок ответа модели. Исходные кандидаты
сохраняются в candidates.json. valid_fraction относится к финальным вариантам;
submitted_valid_fraction показывает долю допустимых исходных кандидатов. Не следует
сравнивать качество генерации только по доле допустимых вариантов после фильтрации.
Разная стоимость управления, обязательная верификация MAS и предел двух исправлений workflow
являются частью сравниваемых архитектур; их нельзя скрывать при интерпретации метрик.

Приватность обеспечивается составом контекста и разрешённых инструментов, а не изоляцией
файловой системы ОС. Нельзя добавлять планировщику произвольное чтение файлов, Python,
shell или доступ к evaluation/. Seed определяет порядок заданий; он не гарантирует
побайтовую воспроизводимость ответов будущей модели. Синтетические признаки, один город
и один уикенд ограничивают обобщаемость результатов.

## Остановка и учёт реальных запросов

Неизвестные или некорректные токены блокируют следующие действия даже без денежного лимита;
стоимость остаётся null. Отсутствие тарифов при известных токенах также не превращает
стоимость в ноль. Перед вызовом резервируются вход и максимальный выход, для входа берётся
больший из обычного и кэшированного тарифов. Usage полученного ответа учитывается до разбора
его содержимого. Ответы failed/incomplete не принимаются как завершённый результат.
Таймаут ограничен оставшимся временем архитектуры. Таймауты, ошибки соединения/сервера
и ошибки декодирования с неизвестной стоимостью останавливают выполнение без повторов.
Только явный rate limit допускает до трёх попыток с учётом общего лимита попыток.
Ошибки запуска и неизвестная стоимость останавливают всю реальную серию после сохранения
результата; продолжение требует разбора трассы, а при неизвестной стоимости — сверки биллинга.

Режим клиента и тип среды учитываются раздельно: mode=real означает вызовы модели,
evaluation_mode=benchmark_assumptions и synthetic=true означают синтетические условия.
Mock-клиент имеет mode=test и mock_client=true. Реальная модель на синтетическом benchmark
не является ни mock-экспериментом, ни проверкой реальной доступности билетов/номеров.
Хеш версии включает src, prompts, configs, scripts и декларации зависимостей.

## Будущий ограниченный пилот

Предварительный кандидат зафиксирован как `openai/gpt-4.1-mini` через OpenRouter.
Адаптер использует совместимый с OpenAI Chat Completions endpoint
`https://openrouter.ai/api/v1`, вызов функций и JSON Schema. Маршрутизация закреплена
за endpoint OpenAI (`order = ["openai"]`), fallback отключён, а
`require_parameters = true` исключает endpoint, который не поддерживает параметры запроса.
Это уменьшает скрытую вариативность между архитектурами.

API по умолчанию выключен. Ключ передаётся только через `OPENROUTER_API_KEY`;
файл `.env` игнорируется Git и не загружается приложением автоматически. Наличие ключа
ничего не включает: нужны одновременно `api_enabled = true` в `configs/llm.toml` и
CLI-флаг `--allow-api`. Первый вызов допускается только после отдельного разрешения.
Подробная конфигурация, тарифы и источники описаны в [openrouter.md](openrouter.md).

Из корня репозитория будущая последовательность команд:

```powershell
python -m pip install -e '.[api]'
python -m pip freeze > reports/local/api-environment-lock.txt
python -B scripts/run_experiments.py --config configs/pilot.example.toml --split dev --scenario dev_01 --repeats 1 --dry-run
# Только после отдельного разрешения сначала выполнить один ограниченный запрос:
python -B scripts/smoke_openrouter.py --allow-api
# Затем провести один пилотный повтор:
python -B scripts/run_experiments.py --config configs/pilot.example.toml --split dev --scenario dev_01 --repeats 1 --allow-api
# Продолжение той же серии с неизменными входами, после разбора возможных ошибок:
python -B scripts/run_experiments.py --config configs/pilot.example.toml --split dev --scenario dev_01 --repeats 1 --allow-api --resume
python -B scripts/evaluate_runs.py --runs runs/pilot --output reports/pilot
python -B scripts/build_report.py --input reports/pilot --output reports/pilot
```

Пример ограничивает каждый из трёх запусков $0.50, всю серию $0.60, архитектуру 48 попытками,
300000 входных и 60000 выходных токенов, 120 инструментами, тремя вопросами и 900 секундами;
максимальный выход одного вызова — 8000 токенов. Денежный лимит может остановить запуск раньше
токенных лимитов. Резервирование использует консервативную оценку входа, а фактический usage
остаётся единственным источником расхода. Для smoke-test действует отдельный предел $0.01,
одна попытка и максимум 128 выходных токенов. Дополнительно следует установить лимит ключа
OpenRouter не выше $0.60 на всю первую серию.
Не увеличивать бюджет одной архитектуры отдельно; сначала разобрать dev-трассы всех трёх.
Команды этого раздела являются инструкцией на будущее, а не свидетельством API-запуска.
