# Протокол сравнения

## Общие условия

Один сохранённый проверенный каталог, точная модель, параметры генерации,
инструменты, три вопроса, формат планов и ограничения ресурсов общие для A/B/C.
В MAS ресурсы суммируются по координатору и всем специалистам. Диспетчер
последовательный. Внешних API предложений, карт и отзывов нет.

API выключен. До предоставления ключа и нового разрешения пользователя разрешены
только программные тесты и dry-run матрицы. ScriptedClient существует только
как явно внедряемая тестовая зависимость. Команды реальных экспериментов не
используют его автоматически даже при ошибках настройки или API.

## Различия архитектур

- Workflow имеет фиксированные этапы analysis/search/clarification/generation,
  затем программную проверку и максимум два LLM-исправления каждого кандидата.
- Single-agent самостоятельно выбирает порядок атомарных инструментов и ремонт.
- MAS: координатор направляет подзадачи transport/stay/places/logistics/verification.
  Специалисты имеют раздельные истории и самостоятельно выбирают инструменты.
  Перед completed-ответом необходимо обратиться ко всем пяти специальностям.

Общая финализация не создаёт и не исправляет маршруты: она валидирует, удаляет
дубликаты, выделяет Парето-фронт и ранжирует. Сохраняется и исходная выдача.

## Приватность

Планировщики получают только публичный сценарий, ответы инструментов и ответы
на заданные вопросы. В registry нет файловой системы, оценщика или эталона.
Симулятор хранит только ответы, не возвращает профиль целиком. Оценщик работает
после завершения планирования. Hash закрытого профиля хранится в манифесте,
сам профиль не передаётся модели.

## Признаки и выбор

Culture/food/comfort: среднее сохранённых подтверждённых оценок выбранных
объектов (0–100, делённое на 100); без подтверждения признака его вклад нулевой.
Pace = max(0, 1 − ходьба / (120 × дни)); economy = max(0, 1 − стоимость / бюджет).
Это исследовательские формулы, не измеренные характеристики реальных людей.
Закрытые неотрицательные веса суммируются в 1. Полезность — их взвешенная сумма.

Доминирование учитывает меньшие стоимость, ходьбу и транспортное время и большие
culture/food/comfort. Ранжирование использует равные начальные веса и публичные
или раскрытые интересы. Скрытых весов оно не использует.

Содержательная идентичность: проживание, упорядоченная пара поездов и набор мест.
Дополнительный логистический вариант возможен при других режимах перемещений
и разнице ходьбы минимум 30 минут. Переименования и сдвиги времени не учитываются.

## Метрики

Success@1: первый финальный вариант полностью допустим и utility >= 0.7.
Success@5: это верно хотя бы для одного из максимум пяти разных вариантов
одного запуска. Два повтора — два запуска, не десять кандидатов одного запуска.
Feasible@1/@5 отдельно показывают выполнимость. Финальная корректность,
корректность исходной выдачи и проверенных промежуточных кандидатов разделены.
Пустая выдача на разрешимой задаче даёт нули. Дубликаты не увеличивают Success@5.

Для неразрешимых случаев Success@K = null; отдельно оценивается корректное
выявление конфликта с проверяемым сертификатом. Реализованы два сертификата:
нижняя граница обязательных расходов и закрытое во все даты обязательное место.
Неудача агента сертификатом не является.

После изменения условий оценивается финальная версия запроса. Исходный ответ
сохраняется в events.jsonl; ресурсы и три вопроса общие для обеих версий.
Для изменяемого случая требуются исходный и .final.json контрольные планы.

## Подготовка и воспроизводимость

1. Человек подтверждает факты и их verified_fields, удаляет устаревшие заглушки
   из производного набора по источникам. Исходные материалы остаются неизменными.
2. Контрольный dev_01 проходит full-валидатор; устанавливается бюджет +20%.
3. Для каждого случая заполняются уникальные условия, контрольный план либо
   сертификат. case.public_hash и case.profile_hash фиксируют проверенные входы.
4. Статусы снимка и случаев становятся verified только после ручной проверки;
   manifest.catalog_hash = digest(load_catalogs(...)). Нужны reviewed_by/reviewed_at.
5. Перед API задаются точная модель, поддерживаемые generation-параметры,
   проверенные тарифы, денежный потолок запуска и серии.
6. После разрешённого пилота на dev_01 замораживаются конфигурация, данные и код.
7. Два блока по 36 запусков перемешиваются Random(seed + repeat).

Логи включают запросы/ответы, действия, ошибки, токены, повторы, время и стоимость.
При неизвестном usage стоимость = null; серия останавливается до сверки биллинга.
Результаты не перезапускаются ради повышения успеха. Interrupted-папки не
перезаписываются автоматически. Resume запрещён при изменении подписи серии.
Ответы провайдера сохраняются; побитовая повторяемость новых генераций не обещается.

При 12 сценариях и двух повторах выводы описательные. Таблица содержит число
наблюдений, среднее и диапазоны; нельзя заявлять доказанное превосходство MAS
по одному успешному примеру.
