## Текущий запуск без API

Нужен Python 3.11+. Для ядра и тестов сторонние пакеты не требуются.

```powershell
python -B -m unittest discover -s tests -v
python scripts/audit_data.py --data-dir data --json
python scripts/prepare_snapshot.py --check
python scripts/check_benchmark.py
python scripts/run_experiments.py --dry-run
```

Аудит исходных данных сейчас возвращает код 2: четыре файла несовместимы с
исходным контрактом. Производный `data/benchmark/snapshot` загружается, но
сохраняет неподтверждённость фактов. `check_benchmark` возвращает код 3.
Dry-run только печатает матрицу из 72 заданий, не создаёт результаты экспериментов.

Для полной проверки предложенного плана:

```powershell
python scripts/check_scenario.py --scope full --scenario dev_01 --data-dir data/benchmark --plan PATH_TO_PLAN.json --json
```

Проверки первого дня доступны прежней командой без `--scope full`.
Полный валидатор возвращает тот же приоритет кодов 2 → 1 → 3 → 0 и не принимает
неизвестную обязательную цену, расписание или доказательство за успех.

Архитектуры: workflow с фиксированными этапами, один автономный агент и
координатор с пятью автономными специалистами. Общие инструменты не строят
маршрут за них. Вопросы и ресурсы ограничены на весь запуск, включая MAS.

## Возможности

- строгая проверка структуры и типов семи входных JSON-файлов;
- поддержка шаблонов с неизвестными значениями `null`;
- диагностика отсутствующих файлов, повреждённого JSON и неизвестной версии схемы;
- проверка уникальности ID и согласованности `snapshot_id`;
- индексы транспорта, проживания, мест, питания, перемещений и станций;
- проверка типа каждой ссылки в ручном плане;
- проверка `start_at < end_at` для заполненных событий;
- обнаружение всех пересечений, включая вложенные интервалы;
- корректная работа со смежными и ночными событиями;
- человекочитаемый и JSON-вывод;
- предсказуемые коды завершения для автоматизации.

Валидатор только читает `data/`: он не изменяет исходный план, `validation_status` или `total_cost_kopecks`.

### Коды завершения

| Код | Значение |
| ---: | --- |
| `0` | Все реализованные проверки полностью выполнены и пройдены |
| `1` | Найдено нарушение реализованного правила |
| `2` | Ошибка чтения, UTF-8, JSON, схемы, типа или заполненного формата |
| `3` | Нарушений не найдено, но данных недостаточно для полного результата |

При сочетании состояний действует приоритет `2 → 1 → 3 → 0`.

### Как проходит проверка

1. `schemas.py` проверяет обязательные ключи, точные типы, перечисления, даты и временные отметки.
2. `catalog.py` независимо загружает семь файлов и сохраняет конкретные ошибки с именем файла и JSON-путём.
3. `validator.py` строит индексы, проверяет ссылки, интервалы и пересечения.
4. `check_scenario.py` форматирует результат и выбирает код завершения.

Ядро не печатает в консоль:

```python
from src.catalog import load_dataset
from src.validator import validate_plan

dataset = load_dataset("data", "dev_01")
report = validate_plan(dataset)

print(report.exit_code)
print(report.to_dict())
```

## Входные данные

В репозитории находятся семь согласованных JSON-файлов версии `0.1.0`.

| Файл | Содержимое |
| --- | --- |
| `data/snapshot/transport.json` | Поезда и встроенные станции |
| `data/snapshot/stays.json` | Варианты проживания |
| `data/snapshot/places.json` | Места и достопримечательности |
| `data/snapshot/food.json` | Варианты питания |
| `data/snapshot/transfers.json` | Направленные перемещения между точками |
| `data/scenarios/dev/dev_01.json` | Запрос пользователя и ограничения |
| `data/reference_plans/dev_01.json` | Ручной план поездки |

Сценарий — это входная задача. Reference plan — выбранное вручную решение. Одинаковое имя файла не означает одинаковое содержимое.

### Общая оболочка каталогов

Пять файлов в `snapshot/` имеют одинаковый верхний уровень:

```json
{
  "schema_version": "0.1.0",
  "snapshot_id": "snapshot_dev_001",
  "is_template": true,
  "timezone": "Europe/Moscow",
  "items": []
}
```

- `schema_version` определяет версию структуры;
- `snapshot_id` должен совпадать во всех связанных файлах;
- `is_template` сообщает о незавершённости данных, но не отключает проверки;
- `timezone` задаёт часовой пояс набора;
- `items` содержит записи каталога или события плана.

## Правила данных

### `null`, `0`, `false` и пустой список

Эти значения имеют разный смысл:

- `null` — значение неизвестно или пока не заполнено;
- `0` — известное нулевое значение, например бесплатный вход;
- `false` — подтверждённое отсутствие свойства;
- `[]` — известный пустой список;
- `constraints.max_walking_minutes_per_day: null` — ограничение на ходьбу не задано.

Валидатор не подменяет `null` нулём и не преобразует строку, дробное число или `bool` в целое. Отсутствие обязательного ключа является ошибкой, даже если его допустимое значение может быть `null`.

### Деньги

Все суммы записываются целым числом копеек:

```json
{
  "amount_kopecks": 125000,
  "currency": "RUB",
  "price_unit": "adult_ticket",
  "price_kind": "listed",
  "includes_mandatory_fees": true
}
```

Поддерживаемые `price_kind`:

- `unknown` — цена неизвестна;
- `listed` — цена взята из источника;
- `estimated` — оценка;
- `free` — подтверждённо бесплатно, сумма должна быть равна `0`.

| `price_unit` | Что означает |
| --- | --- |
| `adult_ticket` | Билет одного взрослого в одном направлении |
| `room_night` | Один номер на одну ночь |
| `adult_visit` | Одно посещение для одного взрослого |
| `adult_meal` | Один приём пищи одного взрослого |
| `person_trip` | Одно перемещение одного человека |
| `vehicle_trip` | Машина целиком на одно перемещение |

В будущей проверке стоимость событий `transport`, `visit`, `meal` и `transfer` будет равна цене записи, умноженной на `quantity`. Проживание должно начисляться один раз как `rooms × nights`; события заселения, выселения и отдыха не дублируют его стоимость.

### Источники

Записи каталогов содержат:

```json
{
  "source_url": null,
  "checked_at": null,
  "notes": null,
  "additional_sources": []
}
```

Заполненный `checked_at` — время проверки источника, а не время события поездки. Дополнительный источник имеет вид:

```json
{
  "source_url": "https://example.com",
  "checked_at": "2026-10-01T12:00:00+03:00",
  "supports": ["opening_hours"]
}
```

Один URL не считается подтверждением всех полей автоматически. Происхождение оценок нужно пояснять в `notes`.

### Даты и время

- дата: `2026-10-24`;
- полная временная отметка: `2026-10-24T12:30:00+03:00`;
- `check_in_from` и `check_out_until`: локальное время `HH:MM`;
- длительности задаются целым числом минут;
- расстояния задаются целым числом метров.

Заполненная полная временная отметка обязана содержать часовой пояс. Для события должны выполняться условия:

```text
start_at < end_at
```

Смежные события, у которых `A.end_at == B.start_at`, не пересекаются. Ночной отдых может закончиться на следующий календарный день; `day` обозначает день начала события.

### Часы работы

```json
{
  "date": "2026-10-24",
  "status": "open",
  "intervals": [
    {
      "start_at": "2026-10-24T10:00:00+03:00",
      "end_at": "2026-10-24T18:00:00+03:00"
    }
  ]
}
```

Допустимые сочетания:

| Состояние | Интервалы |
| --- | --- |
| `unknown` | `null` |
| `closed` | `[]` |
| `open` | Непустой список корректных интервалов |

Структура часов проверяется уже сейчас. Сопоставление посещения с часами работы относится к следующему этапу.

## Справочник каталогов

### Транспорт

`transport.json` содержит направления `outbound` и `return`. Станции встроены в `from_station` и `to_station` и имеют собственные устойчивые ID.

Повтор одного station ID допустим. Известные `name`, `city` и `address` должны совпадать во всех появлениях. `null` в одной копии и известное значение в другой не считаются конфликтом.

Цена относится к одному взрослому. `service_date` — дата отправления с выбранной станции. Состояние доступности принимает значения `unknown`, `available` или `unavailable`.

### Проживание

`stays.json` содержит даты заселения и выселения, локальное время, вместимость, число запрошенных гостей и номеров, доступность завтрака и хранения багажа.

Цена `room_night` относится к одному номеру на одну ночь. `breakfast_included` и `luggage_storage_available` должны оставаться `null`, пока условия не подтверждены.

### Места

В `places.json` поле `category` является свободной строкой, например `museum`, `park`, `walk` или `viewpoint`.

`ticket_required` и `booking_required` — независимые свойства. Бесплатное посещение задаётся явно через `amount_kopecks: 0` и `price_kind: "free"`.

### Питание

`food.json` использует `meal_types` со значениями:

- `breakfast`;
- `lunch`;
- `dinner`;
- `snack`.

Весь список может быть `null`, пока типы питания неизвестны. `price_basis` объясняет оценку расходов на одного взрослого за один приём пищи.

### Перемещения

`transfers.json` описывает направленные связи `from_id → to_id`.

- `mode`: `walk`, `public_transport`, `taxi` или `null`;
- `duration_kind`: `unknown`, `estimated`, `timetable`, `measured`;
- `applicable_date`: дата, для которой собраны сведения;
- `from_id` и `to_id`: ID станции, проживания, места или питания.

Обратный путь является отдельной записью. Пересадки, ожидание и зависимость от времени суток нужно фиксировать в длительности, отдельных событиях или `notes`.

## Сценарий и ручной план

Сценарий содержит:

- города и даты;
- количество взрослых и ночей;
- общий бюджет группы;
- мягкие предпочтения;
- обязательные места;
- ограничение ходьбы;
- минимальный запас перед обратным отправлением.

Пустой `required_place_ids` означает отсутствие обязательных мест. Интерес к музеям или прогулкам сам по себе не превращает конкретное место в обязательное.

Ручной план содержит выбранное проживание и непустой список событий:

```json
{
  "id": "event_01",
  "day": 1,
  "type": "transport",
  "reference_id": "train_out_01",
  "label": "Поезд туда",
  "start_at": null,
  "end_at": null,
  "quantity": 2
}
```

| Тип события | Допустимая ссылка |
| --- | --- |
| `transport` | Запись `transport.json` |
| `transfer` | Запись `transfers.json` |
| `visit` | Запись `places.json` |
| `meal` | Запись `food.json` |
| `check_in`, `check_out`, `rest` | Выбранная запись `stays.json` |
| `buffer` | Конкретная станция из `transport.json` |

`quantity` обязательно для `transport`, `transfer`, `visit` и `meal`. У `meal` также требуется `meal_type`.

## Отчёт

Отчёт содержит:

- `scope: "day1"`;
- ID сценария и снимка;
- `is_template` каждого файла;
- количество загруженных объектов и событий;
- количество корректных полных интервалов;
- результаты отдельных проверок;
- агрегированные нарушения и неполные данные;
- ошибки входных файлов;
- перечень ещё не реализованных проверок;
- `full_trip_feasibility_evaluated: false`.

Каждая проверка имеет один из четырёх статусов:

| Статус | Значение |
| --- | --- |
| `passed` | Все необходимые данные проверены, нарушений нет |
| `failed` | Найдено конкретное нарушение |
| `incomplete` | Проверена только известная часть данных |
| `skipped` | Проверка не выполнена из-за недоступной зависимости |

Если одновременно найдены нарушение и неизвестные значения, статус остаётся `failed`, а обе группы сведений сохраняются в отчёте.

Каждая проблема содержит стабильный `code`, понятное сообщение, файл, JSON-путь и связанные ID, когда они применимы.

## Тесты

```powershell
python -m unittest discover -s tests -v
```

Тестовые данные создаются отдельно от `data/`. Покрыты следующие случаи:

- загрузка шаблонов с `null`;
- последовательные, смежные и ночные события;
- равные и обратные границы интервала;
- обычные и вложенные пересечения;
- пересечение при наличии другого неполного события;
- отсутствующие ссылки и ссылки неверного типа;
- дубли ID и конфликты станций;
- несовпадающий snapshot и неизвестная версия схемы;
- повреждённый JSON и отсутствующий файл;
- неверный тип денежной суммы;
- timestamp без часового пояса;
- пустой список событий;
- оба режима CLI и все основные коды завершения.

Текущий результат:

```text
Ran 11 tests
OK
```

## Работа с данными в команде

Предлагаемое распределение ответственности:

| Область | Ответственность |
| --- | --- |
| Транспорт, проживание, цены | Участник 1 |
| Места, питание, перемещения, ручной план | Участник 2 |
| Схемы, загрузчик, индексы, валидатор | Участник 3 |

Перед общей проверкой нужно:

1. согласовать даты и заполнить бюджет сценария;
2. заполнить выбранные предложения, цены и единицы расчёта;
3. добавить источники и время их проверки;
4. подтвердить доступность для нужных дат и состава группы;
5. заполнить времена всех событий;
6. указать реальные перемещения и их длительность;
7. проверить питание, ночной отдых, багаж, заселение и выселение;
8. удалить неиспользуемые заготовки или оставить их честно помеченными шаблонами.

Не следует менять ID, структуру или `is_template` только ради успешной проверки. Корректный JSON и существующие ссылки ещё не доказывают выполнимость поездки.

## Ограничения текущей версии

Пока не реализованы:

- расчёт бюджета и сверка `total_cost_kopecks`;
- проверка посещений по часам работы;
- проверка длительности и достаточности перемещений;
- сопоставление событий со временем поездов;
- проверка доступности предложений;
- проверка дат, вместимости и условий проживания;
- учёт багажа, завтрака и дополнительных расходов;
- проверка лимита ходьбы и запаса перед отправлением;
- оценка предпочтений пользователя;
- полная оценка выполнимости маршрута;
- LLM, workflow, single-agent и multi-agent режимы;
- внешние API и пользовательский интерфейс.

## Roadmap

Следующий этап:

1. заполнить реальные данные команды;
2. независимо пересчитать полную стоимость;
3. сопоставить события с часами работы и временем транспорта;
4. проверить длительность каждого перемещения;
5. проверить условия проживания и обращение с багажом;
6. реализовать итоговую проверку выполнимости;
7. только после стабилизации детерминированного ядра подключать внешние API, LLM и MAS.

Ручной план в `data/reference_plans/dev_01.json` — контрольный пример, а не единственно допустимый маршрут. Будущие генераторы смогут предложить любое решение, которое удовлетворяет сценарию и подтверждённым фактам.
