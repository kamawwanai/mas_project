Ты работаешь в репозитории учебного проекта «Поездка: бюджет и маршрут».

Реализуй задачи третьего участника команды на ПЕРВЫЙ ДЕНЬ: типизированные схемы данных, загрузку фиксированного каталога, проверку ссылок и две базовые проверки расписания. Нужен работающий код с проверками и инструкцией запуска. Сначала изучи проект, затем внеси изменения и проверь результат.

## 1. Контекст и границы работы

Команда из трёх человек:
- первый собирает транспорт, проживание и сведения о ценах;
- второй собирает места, питание, перемещения и ручной маршрут;
- моя роль — общий программный каркас, модели, загрузчик и валидатор.

Текущий этап работает с локальными JSON. Расчёт бюджета, проверка часов работы, достаточности перемещений, условий заселения, полной выполнимости поездки и предпочтений относятся к следующим задачам. LLM, workflow, одиночный агент, MAS, внешние API и интерфейс пользователя также будут реализованы позже.

Не расширяй текущую задачу до этих компонентов. Учти существующие поля для них в моделях и явно отрази в отчёте, какие проверки ещё не реализованы.

## 3. Контракт данных

Источником названий полей являются фактические JSON; семантику уточняй по README. Не заменяй согласованный формат новым.

Пять каталогов имеют верхнеуровневые поля:
schema_version, snapshot_id, is_template, timezone, items.

Записи каталогов находятся в items. У сценария параметры запроса находятся на верхнем уровне. В items ручного плана находятся события.

Общие важные структуры:
- цена: amount_kopecks, currency, price_unit, price_kind, includes_mandatory_fees;
- источник: source_url, checked_at, notes, additional_sources;
- станция встроена в from_station / to_station записи транспорта;
- часы работы: opening_hours с датой, status и intervals;
- сценарий: id, даты, adults, nights, budget_kopecks, preferences, constraints;
- ручной план: id, scenario_id, selected_stay, items, total_cost_kopecks, validation_status, unresolved_items;
- selected_stay: reference_id, rooms, nights;
- событие: id, day, type, reference_id, label, start_at, end_at; quantity и meal_type присутствуют у соответствующих типов.

Правила:
1. null в предусмотренных шаблонами полях допустим при загрузке. Это неизвестное значение, а не 0, false или пустая строка.
2. У constraints.max_walking_minutes_per_day значение null специально означает отсутствие ограничения.
3. is_template — метаданные. true не запрещает проверять известные значения; false не делает неполные данные полными.
4. Денежные суммы — целые копейки. Не допускай незаметного преобразования дробных сумм, строк или bool в целое денежное значение. Количества должны быть положительными целыми; известные суммы и длительности неотрицательными.
5. Предусмотренные контрактом ключи должны присутствовать, даже если их значение может быть null. Не превращай опечатку или отсутствие обязательного ключа в незаметное значение по умолчанию.
6. Непустое значение неправильного типа или формата — ошибка, а не неизвестность.
7. Даты и заполненные временные отметки должны разбираться как даты/время. Полные временные отметки требуют часового пояса. check_in_from и check_out_until имеют отдельный формат локального времени HH:MM.
8. Для opening_hours различай unknown + intervals=null, closed + intervals=[] и open + непустые интервалы. На этом этапе проверяй структуру, а сопоставление с посещениями оставь следующему этапу.
9. Сохраняй существующие значения перечислений из README, включая единицы цены и типы событий. category может быть свободной строкой.
10. Не зашивай в код даты, города, два человека, конкретные ID и количество записей. Эти значения берутся из файлов.

## 4. Что реализовать

Используй Python и принятые в проекте средства моделирования и тестирования. Если проект пока пустой, выбери минимальный набор зависимостей и зафиксируй установку. Не добавляй тяжёлые фреймворки ради этой задачи.

Предлагаемое разделение, если в проекте ещё нет подходящей структуры:
- src/schemas.py — типизированные модели всех входных данных и отчёта;
- src/catalog.py — загрузка файлов и индексы объектов;
- src/validator.py — проверки и сборка отчёта;
- scripts/check_scenario.py — CLI;
- tests/ — небольшие независимые тестовые примеры;
- README.md — установка, запуск и ограничения первого этапа.

При существующей структуре адаптируй её, сохранив понятные границы ответственности.

Предусмотри простые функции для загрузки каталога, сценария, ручного плана и проверки плана. Ядро проверки должно возвращать структурированный результат без печати в консоль. Форматирование и код завершения относятся к CLI.

### 4.1. Загрузка и схемы

Загружай UTF-8 JSON и валидируй каждый файл по соответствующей модели. Различай:
- отсутствующий или недоступный файл;
- повреждённый JSON;
- ошибку структуры/типа/формата;
- корректную структуру с неизвестными данными.

Сообщай конкретный файл и поле. На ожидаемых ошибках входных данных CLI должен выдавать понятную диагностику без необработанного traceback.

Набор исходных шаблонов с null должен загружаться. Пустой список событий ручного плана считай ошибкой входной структуры; неизвестные времена существующих событий допустимы.

### 4.2. Индексы и ссылки

Проверь:
- уникальность ID записей каталогов и ID событий;
- отсутствие неоднозначного совпадения ID станции с ID другого объекта;
- одинаковый snapshot_id у связанных файлов;
- совместимость schema_version; неизвестную версию явно диагностируй;
- соответствие plan.scenario_id загруженному сценарию;
- selected_stay.reference_id ссылается на запись stays;
- required_place_ids, если указаны, ссылаются на существующие places; проверять наличие этих посещений в расписании пока не нужно;
- from_id и to_id перемещений ссылаются на конкретные станции, проживание, места или питание.

Типы ссылок событий:
- transport → transport;
- transfer → transfers;
- visit → places;
- meal → food;
- check_in, check_out, rest → выбранное проживание;
- buffer → конкретная станция.

Станции извлекай из from_station и to_station. Повтор одного station ID в нескольких поездах допустим. Противоречащие известные характеристики одного station ID — ошибка. null в одной копии и заполненное значение в другой не являются противоречием; при необходимости объединяй известные сведения только во внутреннем индексе, не меняя JSON.

Не перезаписывай молча дубли в словаре.

Если файл не прочитан или не прошёл схему, пропусти зависящие от него проверки с причиной. Не создавай десятки ложных ошибок ссылок из-за одного отсутствующего каталога. Независимые проверки выполняй, когда это возможно.

### 4.3. Проверка интервалов событий

Для каждого события:
- при двух известных корректных временных отметках проверь start_at < end_at;
- при null хотя бы в одной границе отметь интервал как неполный;
- равные границы и окончание раньше начала — нарушения;
- неверный формат или отсутствие часового пояса у заполненной полной отметки — ошибка входных данных.

Сравнивай реальные временные моменты, а не строки. Интервал ночного отдыха может пересекать полночь и заканчиваться на следующий день.

Не заменяй отсутствующее время предполагаемым. Не используй неполные или некорректные интервалы в поиске пересечений.

### 4.4. Проверка пересечений

Проверь все пары доступных корректных интервалов; для небольшого расписания допустим простой попарный алгоритм.

Условие пересечения:
A.start < B.end AND B.start < A.end.

Смежные события, где A.end == B.start, не пересекаются.

Обязательно учитывай вложенные события. Например, 09:00–14:00 пересекается и с 10:00–11:00, и с 12:00–13:00. Сравнения только соседних событий после сортировки недостаточно.

Если между двумя заполненными событиями стоит событие с null, известное пересечение всё равно должно обнаруживаться.

Неполные интервалы не мешают найти известное нарушение, но не позволяют подтвердить отсутствие пересечений во всём расписании. Если проверена только часть событий, укажи это явно.

Интервал всей брони проживания не добавляй в расписание: selected_stay — отдельная структура, а проверка работает с items.

## 5. Отчёт

Результат должен быть машиночитаемым и содержать:
- scope: day1;
- ID сценария и snapshot_id;
- метаданные is_template;
- количество загруженных объектов по категориям;
- количество событий и количество корректных полных интервалов;
- результаты каждой реализованной проверки;
- обнаруженные нарушения;
- неполные данные и причины пропусков;
- список ещё не реализованных проверок;
- явное указание, что полная выполнимость поездки не оценивалась.

Для отдельной проверки различай passed, failed, incomplete и skipped:
- passed — все необходимые для неё данные проверены, нарушений нет;
- failed — обнаружено конкретное нарушение;
- incomplete — нужные данные неизвестны, полного вывода нет;
- skipped — проверка не выполнялась, например из-за ошибки зависимости.

Если найдены нарушения и одновременно есть неизвестные значения, сохрани обе группы сведений, а результат проверки обозначь failed.

У сообщения о проблеме нужны стабильный код, понятный текст, файл и путь поля либо ID объекта; для пересечения — ID обоих событий.

Отсутствующая цена не является ошибкой временной проверки: бюджет ещё не входит в scope. Нереализованные проверки и is_template сами по себе не меняют успех реализованных проверок. Итог должен называться «проверки первого дня», без утверждения о допустимости всей поездки.

Не изменяй входные validation_status и total_cost_kopecks. Отчёт сформируй отдельно.

## 6. CLI

Из корня проекта должна работать команда:

python scripts/check_scenario.py --scenario dev_01

По умолчанию она читает:
- data/snapshot/*.json из списка пяти каталогов;
- data/scenarios/dev/<scenario_id>.json;
- data/reference_plans/<scenario_id>.json.

Добавь --data-dir PATH для отдельного набора данных и --json для вывода отчёта как JSON. Без --json выведи читаемую русскую сводку. В JSON-режиме stdout должен содержать только JSON.

Документируй необходимые установочные команды. Основной запуск не должен требовать ручной настройки PYTHONPATH.

Коды завершения:
- 0 — все реализованные проверки выполнены и пройдены;
- 1 — обнаружены нарушения реализованных правил;
- 2 — ошибка чтения, JSON, схемы или заполненного формата;
- 3 — известных нарушений нет, но данных недостаточно для части реализованных проверок.

При сочетании состояний приоритет: 2, затем 1, затем 3, затем 0. Нереализованные проверки не препятствуют коду 0, но всегда перечисляются отдельно.

Для исходного набора шаблонов с неизвестным временем ожидается код 3, а не авария и не заявление «маршрут допустим». Если команда уже заполнила данные, результат должен соответствовать фактическому содержимому.

## 7. Проверка реализации

Подготовь небольшие синтетические фикстуры отдельно от data/. Они предназначены для проверки программы, а не являются реальными предложениями поездки. Используй принятый в репозитории инструмент тестирования и параметризацию, где это удобно.

Проверь содержательные случаи:
1. Шаблоны с null загружаются; временные проверки возвращают incomplete.
2. Заполненные последовательные события, смежные границы и ночной интервал проходят проверки.
3. Равные границы и окончание раньше начала обнаруживаются.
4. Обнаруживаются обычные и вложенные пересечения.
5. Известное пересечение обнаруживается даже при наличии другого неполного события; итоговый код — 1.
6. Несуществующая ссылка, ссылка неверного типа и дублирующийся ID обнаруживаются.
7. Повтор станции допустим; null и известное значение совместимы; два конфликтующих известных значения обнаруживаются.
8. Повреждённый JSON, отсутствие файла, неверный тип денежной суммы и заполненная временная отметка без часового пояса дают понятную диагностику и код 2.
9. is_template=false при неизвестном времени не превращается в успех; is_template=true позволяет выполнить проверки известных значений.
10. CLI работает в обычном и JSON-режиме, корректно возвращает коды завершения и не изменяет исходные данные.

Не подгоняй тесты под фиксированное количество записей в командных JSON. Для положительного теста используй отдельный небольшой согласованный учебный набор.

Запусти тесты и CLI на доступном фактическом dev_01. Устрани обнаруженные ошибки. Если среда не позволяет выполнить часть проверки, укажи, что именно не запускалось и почему.
